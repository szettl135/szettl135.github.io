*Written by David Grünberger, Caroline Labres, Katharina Wurm, Jan Weiß, Sebastian Zettl, Andreas Kaiser, Felix Kargl and Matthias Frankowski*

In the third semester of the Interactive Technologies master’s program (Mobile Masterclass), we undertook a major semester-long group project. As  an entire master’s class (8 people in total), we spent the  entire semester developing bHere, a social app that uses  game-like mechanics and consequences to motivate groups to put away their phones when  going out together.

## Project Brief

The only requirement was that the project had to include a technical  challenge. After brainstorming three ideas, we decided to develop an app that encourages people to spend more quality time with their loved ones without looking at their phones. The technical challenge lay primarily in connecting the devices via Bluetooth, but also in creating a native, production-ready app.

### MVP

Initially, we defined an MVP with the most basic features. These included the ability for users to log in or register and start sessions during which the phone should not be used. It is also important to establish and maintain the connection between the devices (whether via NFC, BLE, etc.). The app should detect when someone is using their phone and communicate this to the other devices. We had the idea that users could play multiple modes, though only the “Bill Splitter” is part of the MVP. In this mode, users should be able to enter a bill amount, and the app would show who ultimately has to pay how much, based on how often each person’s phone was used. The app should be developed natively on both platforms (iOS and Android) and be production-ready by the end. We also planned to set up a CI/CD pipeline for the backend and develop a website with legal information and links to the app. The website plays a key role, especially for the releases in the app stores.

### Nice To Have

As a “nice-to-have” feature, we primarily set out to add two additional modes: In “Pot Lock” mode, players initially decide how much each person should contribute to a virtual pot and at what mobile phone usage threshold they lose their stake. At the end, the people who haven’t exceeded the threshold split the pot. In “Group Jar” mode, the group sets a price per mobile data usage, and at the end of the session, the app tells everyone how much they need to pay into the group fund.

Other nice-to-haves included the ability for players to join a session in the middle (if someone is late, for example), to reconnect after a disconnect, and to leave the session early (if someone needs to go home early, for example). Apart from that, we wanted the app to work completely offline so that it could be used even in a basement bar with poor reception. Additionally, we wanted to release the app in at least one app store.

We also had lots of cool ideas for enhancing the app with features like mini-games, an AI-powered receipt-scanning function (for the “Bill Splitter”), a history feature, a streak feature, real-time voting (for emergency situations where cell phone use is tolerated), SSO login, and direct in-app payment or an import feature to apps like Splitwise or Tricount—but unfortunately, there wasn’t enough time left for that—at least this semester. 😉

## Technologies Used

### App

The apps were each written natively, in Swift for iOS and Kotlin for  Android, to gain experience in native app development.

### Website

The website was developed using Next.js, a React-based framework. Tailwind CSS was used for styling, and we chose TypeScript for type-safe development. We use a classic component-based architecture with reusable components. We use Docker for containerization.

## Project Process

Work on the semester project was divided into sprints (which were based on masterclass sessions, though we also had occasional internal meetings in between if the gap between masterclass sessions was too long).

We used the “Linear” software as a project management tool and to manage the backlog: before each sprint, we determined who would work on which tickets and assigned them to team members.

## The Final Product

We implemented the MVP features and nice-to-haves as described, with the following minor adjustments: Our app works completely offline using Bluetooth LE, and the session ID is exchanged among players by scanning a QR code. Although we initially set up the backend, it is not currently needed. In addition to the three modes, there is now a fourth mode, the “Basic Leaderboard,” which allows users to set their own rules. We also implemented a solo mode so that the app can be used not only in a group but also on your own (e.g., while studying). Furthermore, we set up a cool CI/CD pipeline for our website and published our app in not just one, but both stores (Apple App Store, Google Play Store).

When you open the app for the first time, you are guided through an onboarding process that briefly introduces the app. Here, you must also enter a  name to be used for yourself within the app. Finally, you arrive at the home screen (Fig. 3, left). Via  the profile icon in the top right corner, you can change the name you’ve set. Clicking the “Start New Session” button starts a  new group session and takes you to the New Session Screen (Fig. 3, center) –  however, only one person in the group needs to click this button.  Everyone else clicks “Join Session,” which opens the camera to  scan the generated QR code, which then also redirects you to the New  Session Screen. The “Go Solo” button leads to Solo Mode,  which is described in more detail below.

The New Session Screen displays the current participants and the selected mode. The session “Host” (the person who clicked “Start New Session”) also has the option to select the mode (Fig. 3, right) and configure necessary settings (e.g., set the price per use for Group Jar mode).

## Feedback and Areas for Improvement

By participating in the project launch event, we were able to gather valuable user feedback for potential future enhancements and improvements to the app: arguably the biggest pain point of the current solution is the latency of the implemented BLE mesh. Especially during sessions with a large number of participants, it can currently take up to several minutes for all data to be exchanged between all devices. If the project were to be further developed, this would likely be one of the first issues that would need to be addressed.

## Conclusion from all participants

In the following section, we would like to share our conclusion and the  experiences we gained during this semester group project.

### David

Working on bHere was an intense and educational experience for me. From a technical standpoint, implementing Bluetooth Low Energy communication was certainly the biggest hurdle. It took several iterations and a lot of research, which is why I’m all the more proud that we were ultimately able to get a functioning BLE mesh up and running.

One important lesson for me was the challenge of developing simultaneously on two platforms. It quickly became clear that if details aren’t clearly defined in advance, they can end up being implemented differently on iOS and Android. As a result, the final weeks and days before the deadline were particularly intense, as we still had to iron out many of these minor inconsistencies. I had also underestimated the  release process—in particular,  preparing the store listing and the mandatory 14-day testing phase in the Google Play Store require more lead time than one might initially  expect.
