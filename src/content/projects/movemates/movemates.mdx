*Written by David Grünberger, Caroline Labres, Katharina Wurm, Jan Weiß, Sebastian Zettl, Andreas Kaiser, Felix Kargl and Matthias Frankowski*

At the beginning of the second semester of the Master’s program in Interactive Technologies (Mobile Master Class), “Extreme Programming Week” (also known as “Wild Week”) took place. For this week, we were given the challenge of developing an app as an entire master’s class (8 people in total) within 5 days (Monday through Friday). We didn’t receive the specific assignment until Monday, and the MVP version was to be presented on Friday afternoon.

## Task Description

The task description and the MVP were largely predetermined, though we were able to have a say, particularly regarding the optional additional features. The basic idea was to develop an app that allows users to share certain real-time data—such as location, speed, heart rate, etc.—with a group. There are several potential areas of application.  For example, one could focus on sports (running, cycling, etc.) or on health (including fall detection). Ultimately, we decided on the “running against each other” category.

### MVP (Minimum Viable Product)


To be able to say in the end that we had mastered the task, we defined an MVP (Minimum Viable Product) with the most basic functions. As far as the client was concerned, the key priorities were reading and meaningfully transmitting sensor data, login and team formation, as well as a “cool presentation.” Especially regarding the last point, we really needed to think about what works well in context, rather than simply displaying all the data as numbers.
On the server side, the focus was on distributing the data in real time within the team.
In addition, the app was to be available natively on at least one platform in test mode.

### NTH (Nice to Have)

In addition to the MVP, optional features—referred to as “Nice to Haves”—were also noted, which would then be implemented once the MVP was complete. This list was expanded throughout the week.
These included distribution on both platforms (iOS and Android) and the introduction of a handicap system that would allow people of varying skill levels to compete against each other in a sport. A history of past sessions, the ability to export data, gamification, the app running in the background, micro-interactions, and vibration were also items on this list. Other ideas included calculating a performance score, tests, or using a QR code for group formation.

It was clear from the start that we wouldn’t have enough time to develop a native version of our app for both Android and iOS, which is why we opted for a cross-platform technology for the front end.

### Frontend

On the frontend, we worked with the cross-platform framework Ionic (Capacitor), in combination with the frontend technology React—written in TypeScript. We chose this approach because, in the first semester of our studies, we had to implement a project using React, and we also worked with the Ionic framework in our master’s class.

We designed the initial screen prototypes using the design software Figma.

### Backend

On the backend, we used NestJS, also in combination with TypeScript, since we had already used this backend technology in a project during the first semester of our master’s program, which eliminated the learning curve.

Since our app relies heavily on live data (both sending a user’s current sensor data and receiving live data from other users during an activity), we decided to use WebSockets for this purpose, which are seamlessly supported in NestJS. When creating a session for all participants, a WebSocket “topic” was created that users could subscribe to in their apps and through which the latest live data was exchanged at a fixed interval.

#### Database

For data persistence, we relied on a PostgreSQL database, supplemented by the object-relational mapper (ORM) TypeORM. We chose PostgreSQL because of its reliability and widespread adoption as a relational database, which provided us with a solid foundation for our application and enabled future scalability. Another decisive factor was its excellent compatibility with NestJS and the team’s existing experience with TypeORM.

The structure of our database is illustrated in this ER diagram. The core entities are User, Session, and Measurement Values. Between :

- User**:** Here we store all necessary user information, including ID, first name, last name, email, password, and physiological data such as date of birth, height, weight, and gender. This information is essential, particularly the date of birth, for calculating individual heart rate zones.
- Session**:** This entity manages the details of running sessions, such as ID, status, end date, type, and start date.
- User_Session**:** As a join table, it represents the relationship between users and sessions and stores the participant’s role within a session.
- Measurements**:** This central entity is responsible for storing the sensor data collected during an active session. This includes timestamps, speed, latitude, longitude, position, direction, heart rate, and step frequency. This data forms the basis for our real-time displays and potential historical analyses.

Our PostgreSQL database thus forms the backbone of our app by storing all static user and session data, as well as the dynamic sensor data required for core functions and visualization.

To keep this database stable and easy to manage, we used Docker. This allowed us to run the PostgreSQL database in its own, isolated “container.” Not only does this simplify setup considerably, but it also ensures that the database always runs in a consistent environment and that its data remains securely stored. Thanks to this Docker setup, our backend service was able to connect to the database smoothly and reliably as soon as it was ready. The configuration with TypeORM, in turn, ensured that our app could read, write, and manage the data correctly. Our TypeORM database migrations were particularly important here. These function like small, versioned scripts that allowed us to adapt the database structure (such as adding new columns or modifying existing ones) incrementally and in a controlled manner throughout development, without losing any data.

#### OpenAPI

To avoid having to list all backend objects twice in our frontend and to save time, we decided to use the OpenAPI Generator. The basic function of this tool is that you define and document the endpoints in the backend using a decorator, such as Swagger. Using this documentation, you can then generate client functions for the frontend that are consistent with the backend and type-safe. In our backend, we used Swagger to specify the endpoint specifications via a decorator. On the front end, we then installed *@openapitools/openapi-generator-cli*, which provides a command that allows you to generate the API. Before that, you need an OpenAPI spec file named *openapitool.json*, in which you specify the settings for the API. After that, you can generate the API at any time and use it.

### CI/CD

A server on our FH Cloud was made available to us for our backend application. Did we upload our NestJS application to this server via FTP? Of course not! Did we instead invest a lot of time in continuous integration and deployment (CI/CD)? Absolutely! On the very first day of the week, we wrote a `docker-compose.yml` file. This allowed us to start the backend application with a Postgres database. With the support of our master class instructor Armin, we installed Docker on our server on the morning of the second day. Then we set up a GitLab Runner with the Shell Executor and wrote the .gitlab-ci.yml file. In it, we defined a deploy job that runs docker-compose whenever there’s a commit to the “main” branch, thereby launching the latest version of the application on our server.  We also automated the build of our Android app. This required a job to install the Ionic app’s dependencies, a job to build the frontend application, a job to build the .apk, and finally a job to publish the .apk. To ensure reproducible builds and a clean server, we wanted to run all these jobs in containers. To do this, we had to set up another GitLab Runner, this time using the Docker Executor.
The Android app build uses the alvrme/alpine-android image, and the others use a simple Node.js image. Continuous deployment was implemented, and continuous integration followed.

When you start a new NestJS project, [Eslint](https://eslint.org/), [Prettier](https://prettier.io/), and [Jest](https://jestjs.io/) are automatically set up. To ensure that code linting/formatting and testing are also executed in the pipeline, we created a separate job for each in a “test” step within our pipeline. Upstream, there is a job that installs the dependencies. All three jobs run in a Node.js image. If we’d had more time, we would have created a linting and testing job for the frontend as well.

#### Internal App Publishing

One of our client's requirements was to make the finished app publicly available on at least one of the two platforms in any way we chose. We decided to use Firebase App Distribution to deliver our Android app to a clearly defined group of people. We set up a build job in our GitLab pipeline that generated an APK file and uploaded it via the Firebase CLI to a closed test environment, to which all team members and our instructors were invited. This way, after every commit to our master branch, a new app version was released, which could be downloaded with a single click in the Firebase App Distribution app.

## Final product delivered

Our app is divided into several clearly organized screens that guide the user step by step through the entire process. From registration to creating or joining a session, all the way to active use during a run, all functions are clearly structured. The focus is on the dashboard as the central control center, the WaitingScreen for organizing participants, and the user profile, where personal data can be managed. During an active session, the leaderboard and the map view take center stage. Here, all relevant information about the participants is displayed in real time. 
However, before the actual process begins, users must first log in or register.

### Login and Registration

When the app is opened for the first time, the user is redirected to the login screen. Here, users can either log in with existing credentials or register for a new account. Registration is completed via a short form that asks for basic information such as username, email address, and password.

### Dashboard

Once the user has logged in or registered, they are taken to the dashboard. Here, two options are available: either create a new session or join an existing session. However, these options are initially grayed out and can only be used once certain requirements have been met.

The dashboard features three buttons for activating the required sensors:

- **GPS**
- **Heart Rate Sensor** (including Bluetooth connection to a wearable)
- **Heading sensor**

Initially, all three buttons are red to indicate that the respective sensors are not yet active. After successful activation—whether by turning on a device sensor or establishing a connection—the color changes to green, visually signaling that the respective sensor is now ready for use.

Only after either the GPS signal or the heart rate sensor has been activated are the two options “Create Session” and “Join Session” enabled and selectable. Optionally, the heading sensor can also be activated, which later allows for a more accurate direction of movement on the map.

When joining a session, you must first enter the session ID—which you received via a QR code or a message—into an input field. You will then be automatically redirected to the next screen.

### WaitingScreen

The current list of participants is displayed on the WaitingScreen. There, the user can see who has already checked in. The list updates automatically as soon as more people join.

Users can leave the session at any time by clicking the “Log Out” button. Doing so will take them directly back to the dashboard. However, if the host clicks “Log Out,” not only will their own connection be terminated, but the entire session will be deleted, including all participants. In this case as well, everyone is automatically returned to the dashboard.

### QR Modal

The session creator has the option to generate a QR code. This button is located above the participant list. Clicking it opens a modal window displaying the QR code. The QR code contains the session ID and can also be copied to the clipboard using a button. Additionally, there is the option to share the session ID directly via message or social media. When the host decides that everyone is ready, the session can be started at any time by clicking the “Start” button.

As soon as the host of a session clicks “Start,” all users in the session appear on the leaderboard. This is the core concept of our app. At the very top of the screen, you’ll find two tabs to switch between two views: the leaderboard and the map view.

### Leaderboard

At the top of the screen, the user will find the ranking display. The user’s own rank is displayed quite large so that they can immediately see where they stand on the leaderboard. Right below that is the most important feature of our app: the visual display of heart rate and speed. We divide heart rate into 3 zones. The middle zone represents the “ideal” heart rate for the user for the current activity. As soon as you’re in the left or right zone, it means  that your heart rate is too low or too high, respectively. The “ideal  heart rate” is calculated based on the user’s age,  to ensure fairness among participants of different ages. We chose a bar chart for the visual representation because it allowed us to color-code the three zones and let the active heart rate move back and forth along the bar. The bars also display the number of points earned based on which zone the user is in. The point system for heart rate was designed so that only the middle zone—Zone 2—earns the most points (+5 points). The other two zones each earn +2 points. Thus, the user is credited with points every 3 seconds, depending on the zone. 

Below the heart rate bar is the speed bar, which works on the same principle. Depending on your speed, the points move upward—the faster you go, the more points you earn. Here, too, the bar is divided into several zones, each marked by a different color.

Below the two bars is the leaderboard. It displays all participants and their scores. All scores are updated continuously every 3 seconds, so the board is constantly in motion. When rankings change, this is shown in an overlapping animation. Additionally, the top three spots are displayed in the classic colors of gold, silver, and bronze.

### Feedback Received: Room for Improvement

During the interactive live demo and following the presentation, we received the following feedback:

- The WebSocket connection frequently drops (e.g., when switching from Wi-Fi to mobile data, and also after a period of inactivity). A way to (automatically) reconnect should be implemented.
- Data calculations (points for the leaderboard) are currently performed on the client side. These calculations should be done on the server side.
- If both the heart rate and GPS data are zero, that person’s visual bar disappears from the leaderboard.
- The code that must be entered to join a session should be shorter. Additionally, a built-in QR code reader would be cool. (We actually planned to include this, but unfortunately didn’t quite have enough time.)
- It would be good to be able to see during the session…
  - …how accurate the data is (e.g., location).
  - …whether a person has a heart rate sensor connected. (It would also be helpful to be able to connect a heart rate sensor during the session, even later on.)
  - …whether a person is currently disconnected.
- Another nice-to-have feature would be the ability to click on individual users in the leaderboard during the session to view detailed information about them. Perhaps the view could also allow users to compare their own data with that of others right away.
